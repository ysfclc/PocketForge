# ADR-0015: Git-native source of truth and direct commit-to-APK CI

- Status: Accepted
- Date: 2026-11-14
- Supersedes: archive-ingestion and target-repository provisioning aspects of ADR-0012/ADR-0013 where they conflict

## Context

The initial Keystone brief described a ZIP-driven control repository that would validate archives, provision target repositories and publish source to those repositories. The product owner clarified that PocketForge is being developed directly in its canonical GitHub repository and that ZIP handoff is not part of the workflow.

## Decision

1. `ysfclc/PocketForge` is the sole source of truth.
2. Every phase is delivered as ordinary Git commits on focused branches and reviewed pull requests.
3. The permanent `.github/workflows/pipeline.yml` checks out the exact event commit, validates repository contracts, builds Rust for Android ABIs, tests/lints Rust, assembles and verifies the Android debug APK, generates an SBOM, attests provenance and uploads the APK artifact.
4. `.github/workflows/android.yml` is reserved for manually dispatched release signing from protected `main`, behind the `android-release` Environment.
5. No ZIP drop zone, archive validator, phase publisher, repository-creation token or secondary repository is maintained.
6. Git commit SHA and Actions run identity are the source provenance. Re-running CI does not create or mutate source commits.

## Consequences

- Simpler and auditable developer workflow; no privileged archive extraction or secondary-repository credentials.
- Pull requests are the review boundary for agent-generated and human changes.
- CI builds source directly and artifacts are attached to the originating workflow run.
- The original ZIP-ingestion skills/scripts and setup instructions are removed or rewritten.
- The repository's acceptance ledger must be updated with exact workflow evidence.

## Alternatives considered

- Keep ZIP ingestion as an optional pathway: rejected because it adds a second source path, attack surface and operational complexity that the owner does not want.
- Publish each phase to a newly provisioned repository: rejected because it fragments history and creates unnecessary token permissions.
- Build only on merge: rejected as the only validation path; pull requests also need compile/test feedback before merge.
